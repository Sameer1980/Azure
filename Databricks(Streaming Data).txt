Scenario 1:

App/Device on cab -> Stream Ingestion ->   Stream Processing  ->     Delta Lake
                     (Azure Event Hubs)    (Structured Streaming)   (Azure Data Lake Gen2)

									   \                             /

Benefits of Streaming on Delta Lake:

-Integrated with Spark Structured Streaming

- Batch and Streaming data can be stored together.

- Streaming upserts can be performed on delta lake.
     - Incremental loads can be performed.
	 
- Multiple streams can write to the same table.
       - Delta tables can handle concurrency.
	   
-Delta Tables can be used as streaming source and sink.

Transaction Log Checkpointing
------------------------------

Checkpoints are written to store the intermediate state.

If we are writing to the Delta table it will create the Transaction Log.(_delta_log(subfolder))

For each transaction a log file will be created in the Transaction Log folder.

000.json
   |
001.json
   |
   |
   |
   |
008.json
009.json     <-------------   Read current >> Reads log till version 9 
010.json     <--------- Write version 10
010.checkpoint.parquet <------------    Writes a checkpoint file every 10 commits 
                                        Saves entire table state at a point in time.
011.json    <-----  Read current >> Reads latest checkpoint at 10 and version 11.So there is no need to read all the previous logs as their information is stored in the latest Checkpoint file.
    |
    |
    |
    |
    |
    |
    |
    |
    |
020.json
020.checkpoint.parquet
	
**** Note :
    - Checkpoint is handled by Delta Lake.
	- Log retention interval is 30 days by default.
	- With checkpoints , versions older than 30 days are removed.

Handling Concurrency
----------------------

Delta Lake uses Optimistic Concurrency.


                         1 - Simultaneous Inserts
Writer A                                           _delta_log               Writer B		
Insert record with Id=2       Id | Name             000.json                Insert record with Id=3
                               1 |  A     
1.Records current version                                                    1. Record current version
(000.json)                                                                      (000.json)

2. Write partition file        Id | Name            001.json                 2. Write partition file
                                2 | B
3. Try to commit changes                                                     3. Try to commit changes to 
  to transaction log           Id | Name            002.json                     transaction log
                                3 |  C
								
								
Both will try to commit the changes to Transaction Log. Both will try to write to the json file(001.json)

Suppose Writer A is able to commit the log first . Writer B is then not able to commit the log file.

This is how Optimistic Concurrency works and that's how Delta Lake provides isolation to transactions.							

In this case Delta Lake will optimistically retry to add a log entry. So it adds another log file (002.json) . 
This is only possible if an insert fails. That's how multiple inserts can work concurrently.

                         
	
                  	               2 - Simultaneous Updates
Writer A	                                         _delta_log                 Writer B					

Update record with Id=1 			  |Id | Name|       Operation |  File       Update record with Id=1			
									   1 |  A	|        Add      |  Part1
1. Record current version                                                       1. Record current version
     (000.json)                       Id  |  Name       Operation | File          (000.json)
                                        1  |  A1         Remove   | Part1
2. Write partition file                                   Add     | Part2       2. Write partition file
                                      Id  | Name
                                       1  |  B1
		
Writer A is trying to update from A to A1 while writer B is trying to update from A to B1.Once done both will try to commit the changes.
Assume that writer A commits first . It mentions that Part1 is no longer required and Part2 is the new file. 
Writer B won't be able to commit the log since file Part1 is now considered removed. 
This is how concurrent updates are handled by Delta Lake.
No retries are performed if an update command fails.

**** How Write conflicts are Handled ?

WriterA                          WriterB                                 Conflict

Insert                            Insert                                 No conflict. Silently handled

Insert                       Update/Delete/Merge                         No conflict. Silently handled

Update/Delete/ Merge          Update/Delete/ Merge                        Can conflict if working on same set of files.
                                                                         Resolve it by making sure that both writers are working on 
                                                                           seperate partitions.
