# How Spark writes to Data Lake ?

We have a Spark cluster and a data lake .

Job (process sales data)

Spark will create a job divided into multiple , parallel tasks to write multiple, partitioned files parallely to the Data Lake folder.

                        |-Task1-------------------------------> part-000.csv    } (partition files)
                        |- Task2------------------------------> part-001.csv    }
Job (process sales data)|- Task3------------------------------> part-002.csv    }DATA LAKE
                        |-Task4-------------------------------->part-003.csv    }
						
#ACID guarantees on transactions.
Atomicity - All or no changes are written .
Consistency - Data always remains in valid state before and after the transaction.
Isolation - Transaction must run isolated from other processes. Any data written by the writer should not be visible to the Reader till it is committed.
Durability - Once committed , data persists even if system fails.

Data Lakes does not provide ACID guarantees.
In Spark overwrite is a 2 step process. Delete existing + write two new part files.

Challenges with Data Lake.
- Data corruption because of failures - no rollback.If the writer process writes part-002 but fails in writing part-003 due to job failure at runtime
  then the Reader will only read part files 1,2 & 3 . This is inconsistent read.
  
- No data validation while writing. So a column could be written as integer in one transaction and string in another.

- Consistency issues while reading data. In Spark overwriting data means deleting existing data. Suppose a process is writing two part files -
    part001 & part002 . Job fails with runtime error. New part file2 could not be written. Reader process reads part001 file only. It reads 
	Inconsistent data + Previous data is lost. This breaks Atocmicity, Consistency and Durability.
	
- Handling Batch and Streaming data together is tough.
- No updates / deletes / merge on files.(Difficult to implement GDPR/CCPA compliance).
- Data quality issues.- Schema isn't verified before writing.
                      - Cannot apply checks on data (like in the databases)
- Query performance issues.
- Difficult to maintain historical versions of data.


Delta Lake can help solve these challenges. Apache Iceberg and Apache Hudi that works similarly to Delta Lake.
Delta Lake is an open source storage layer that brings reliability to Data Lakes.
We need to deploy the Delta Lake component in Spark cluster.
Data from a dataframe will be written using delta format and stored as Parquet files along with transaction log.

Save Dataframe in Delta format.

(
dataframe
   .write 
   .format("delta") # like other formats - csv , parquet , etc.
   .save (filepath)
   
)

Suppose we want to store Customer data in delta format inside Customer folder. Spark will create a _delta_log subfolder where the transaction log will be stored.

Write operation 1 (write 2 part files) - > part-000.parquet and part-001.parquet. Since we are creating in delta format Spark will also create a file called
000.json that will be stored in the _delta_log subfolder and contain transaction log data.

Write operation 2 (append 1 part file) part-002.parquet and 001.json in the  _delta_log subfolder.

Write operation 3 (append 1 part file) part-003.parquet and 002.json in the  _delta_log subfolder.

For update operation(update in part-000 , modify A to AA where Id=1) . A new part file will be created(part-004) , all modifications along with 
 unchanged data from part-000 will be written to part-004 . Part-000 file will be removed.So when log files are read first it will read 
 part-000, then part-001,002,003 and 004. But it will only consider data from part-001,002,003 and 004 since part-000 has been updated and hence
 will be deleted.

For each write operation part files are written first and then a transaction log file is added in json format to _delta_log folder.
Transaction logs contain the details of every transaction that has been performed on the file.

For each read operation first transaction log files are read and part files are then read based on log files.First each all log files - 000.json,001.json , 002.json
and then read 4 part files based on log information. It contains information like operation and file name.
For Update operation log file will contain 2 operations - Remove and add - Remove part1 and add part4.

Delta Lake features - 
Provides ACID guarantees 
- No data corruption because of failures.
- Data consistency while reading data.
- Job failure in appending data . Suppose the writer process is adding two more part part-003 and part-004 . Part-003 is written but part-004
  could not be written due to job failure at run time. The _delta_log (000.json) will only contains information about part-000 and part-001.
  It will contain no information about the failed transaction.(part-003 & 004)and the Reader will read as such.
  In Delta Lake while overwriting , existing files are not deleted. So if there is a job failure and new part file 4 could not be written, the Reader 
  while reading _delta_log(000.json) will only read part files 1 & 2. So it reads consistent data + previous data is not lost.
  
- Simultaneous Read / Write - Two part files (001 & 002) are already written by previous transaction(_delta_log(000.json)).Writer writes two more 
  part files using 2 tasks. Only 003 is written and 004 is getting processed. Simultaneously Reader reads log file while writing is in progress.
  (reads 000.json) . It only reads Part files 1 & 2. No dirty reads while writing is in progress. Writer process is running in isolation.
  Once file 4 (004) is ready it will be added to the folder and an entry will be made in the transaction log(001.json).

DELTA LAKE WITH AZURE DATABRICKS
--------------------------------------

Data Lake is a central repository to store all types of data at any scale in the form of files.

Delta Ecosystem ->

1. Delta Lake Storage . 
     - Open source storage layer that runs on Data Lake.
	 - Adds transaction log along with data (partition) files.
	 - Brings Warehouse like features to data lake.
	 - All other components depends on this.
	 
2. Delta Engine - >
     - Only available in Databricks.
	 - High Performance , vectorized query engine - Photon
	 - Brings a caching feature called Delta Cache.
	 - Has optimizations to improve query performance.

3. Delta Sharing ->
    - Open source protocol for sharing Delta Lake data.
	- Securely share data in real-time stored in S3, ADLS , GCS etc.
	- Consume shared data using multiple engines like Spark, Rust , PowerBI, Pandas , etc.
	
4. Delta Connectors ->
   - Open-source connectors to connect to Delta Lake.
   - Delta Standalone is a native library to work with Delta Lake metadata. 
   - Connectors - Rust library , Kafka ingest , Hive , Presto , PowerBI, etc.
   
 5. Delta Architecture ->
   - Architecture built using Delta Lake Storage.
   - Improves Data Quality.
   - Serves data to business users , data scientists etc.
   - This is part of Lakehouse architecture. 
 
 6. Delta Live Tables ->
    - Only available in Databricks.
	- Framework to build data processing pipelines.
	- Perform transformations and enforce data quality.
	- Use this feature to quickly build Delta architecture.
	
 visit github.com/delta-io to check open source projects .

SCHEMA ENFORCEMENT AND EVOLUTION
-----------------------------------------
                                           _delta_log
PartFile1 - 3 cols                          000.json- 3 cols

PartFile2 - 3 cols 


#Appending Data with new Schema .

Writer process wants to write two more part files using 2 tasks.

New output files have 4 columns.

PartFile3 - 4 cols

PartFile4 - 4 cols 

# Before entry made into transaction log schema validation is performed. Since schema of new dataset does not match with the Delta table 
schema no log file gets generated.

If a reader process wants to read the data it will only read Part Files 1 & 2 since 000.json only refers to these two files. 
So reads consistent data with 3 cols only. 


Schema Enforcement - At commit time , schema of new data is checked with Delta table schema .

Schema mismatch could occur if :
     
	    - Source contains additional columns.
		- Column data types don't match .
		
Column names are case-insensitive 

     - Columns with same name but different case cannot be added to table.
	 
On schema mismatch :

     -   No entry is added to Transaction Log.
	 -   Exception is raised.
	 -  Incorrect partition files are still present in the folder .
	
	
Schema Evolution :
            -   Delta Lake allows adding more columns to table while writing data .  
            - Needs to be defined explicitly.
			- MERGE command supports auto schema evolution.

BUILDING ETL PIPELINES WITH DELTA LIVE TABLES
---------------------------------------------

Delta Architecture 
--------------------

BRONZE LAYER -->  SILVER LAYER ---> GOLD LAYER 

Raw data  --> Cleaned , filtered  --->  Aggregated / 
              & transformed data        Business specific data 


There may be multiple entities holding raw data . Like Customers , Sales ,etc. They may have different data quality issues .

There may be multiple tables in the Silver layer and one bronze table may feed multiple Silver tables. 

There may be multiple tables in the Gold layer based upon business requirements and the data in them might be based on joins in the Silver table.

Complex ETL pipelines challenges :
    - Infrastructure Management & Scaling
    -  Handle Batch & Streaming data 
	- Handle Failures & Retries
	- Monitor , optimize & Maintain.
	- Ensure Data Quality
	- Manage Dependencies .
	- Track Lineage
	- Deployment in multiple environments .
	
Delta Live Tables is an ETL framework to build reliable , automated , testable & declarative ETL pipelines .

Delta Live Pipelines .

Components of Delta Live Tables .

-  Datasets or Delta Tables.
-  Data Quality Checks .
- Queries to define business logic.
- Pipelines
- Environments 

Steps to Create ETL Pipelines.

1. Create Live datasets 
      - Delta tables or views
	  - Types - Complete , Incremental & Streaming 
	  

2. Define data quality checks (expectations) on datasets.
     -   Constraints to apply
	 -   Actions in case of errors
	 
3. Define data transformation queries
     -  Business logic to clean , filter , transform , aggregate 
     - Define inter-dependencies between datasets.
	 
4. Create , run & test pipelines
        - Auto-manage infra , process data , maintain lineage , apply quality checks, handle logs , retry on failures , etc.
		- Mode of execution - Triggered or Continuous 

5. Promote to production

## BUILDING COMPLEX & INCREMENTAL ETL PIPELINE 
-----------------------------------------------

There are two Table types - Complete & Incremental .


Delta Architecture with DLT.
-----------------------------------
'TaxisZones' is a small table so it will be loaded completely every time in the Bronze layer.(Complete Table)
             - A view will be created on this in the Silver layer . (Complete View)
			 
'YellowTaxis' will be loaded incrementally in the Bronze layer. (Incremental Table)
              - This means only the new files from source will be loaded to Bronze table.
			  - We can also implement complex logic by creating a Incremental View on the Incremental(Bronze) Table.
			  - From the Bronze view Silver Table for the 'Yellow Taxis' will be loaded. This will also be a incremental Table since only new data 
			     from Bronze will be loaded into this Table.
				 
'Summary By Date' - Complete Table in Gold layer (Aggregated data from 'Yellow Taxis'). This will reload every time so this will be a Complete Table.


'Summary By Zone' - Complete Table in Gold layer (based upon joins from 'YellowTaxis' [Incr. Table in Silver] and 'TaxiZones' [complete View in Silver]).



Bronze Layer                                               Silver Layer                                   Gold Layer

TaxiZones (Complete Table)  ---->                        TaxiZones (Complete View)    ---|---->           SummaryByZone
                                                                                         |               (Complete Table)
                                                                       |---------------->| 
YellowTaxis        -->  YellowTaxis     ------>             YellowTaxis|--------->                        SummaryByDate
(Incremental Table)   (Incremental View)                   (Incremental Table)                          (Complete Table) 


Supported Scenarios
--------------------------
Read From                     Write To                    What Happpens ?                Scenario          

Complete                      Complete                   Data is overwritten             Taxi Zones 			  
                                                                                        Bronze -> Silver

Complete                      Incremental               Not possible                    N/A


Incremental                   Complete                   Data is overwritten             YellowTaxis
                                                                                       Silver -> Gold

                                                                                         Bronze -> Silver

B.2 Merge Change Incrementally into Silver table.

APPLY CHANGES INTO live.YellowTaxis_SilverLiveIncremental

FROM STREAM (live.YellowTaxis_BronzeLiveIncrementalView)

KEYS (RideId , VendorId)

SEQUENCE BY CreatedOn

** Note :- In DLT there is no MERGE statement so we have to use the 'APPLY CHANGES' command .
          -  Apply changes into the Silver Live Table by picking data from Bronze View . Since we are going to pick data incrementally from Bronze it 
             must be called using STREAM function. 
          -Define the keys to join . Let's join by using 'RideId' and 'VendorId'. The same keys must be present in both the datasets.
		  -SEQUENCE BY sorts the data in Bronze Table so that the changes are applied in sequence.

/* Specify STORED AS SCD TYPE 1 (overwrite) or STORED AS SCD TYPE 2 (history).*/
CREATE OR REFRESH STREAMING TABLE live.YellowTaxis_SilverLiveIncremental;

APPLY CHANGES INTO live.YellowTaxis_SilverLiveIncremental
FROM STREAM(live.YellowTaxis_BronzeLiveIncrementalView)
KEYS (RideId, VendorId)
SEQUENCE BY CreatedOn
STORED AS SCD TYPE 1;
