Joins Optimization
----------------------------------------------------------------------------
So if there is one Fact table of one 1 GB size  --> There will be 8 partitions (as per the default 128 MB size rule) 
There is one Dim table - 1 MB size  --> 1 partition. 

Join is a wide transformations. There are two types of transformations - Narrow and Wide . In narrow there is no shuffling but in wide transformations there is shuffling.


How It Works

- No Shuffling: In a standard join, Spark moves (shuffles) rows with matching keys across the network so they sit on the same executor, which is slow and resource-heavy.
- Copy to All Nodes: A broadcast join sends a complete copy of the smaller DataFrame or table to every worker node (executor) in the cluster.
- Local Joins: Because every worker holds a local copy of the small table, it can perform the join immediately in its own memory without network data movement.
- Stays put in partitions: The large table remains distributed across the cluster in its existing data partitions.
- No network shuffle: Spark does not redistribute, rehash, or sort the large table across the network.
- Local stream processing: Each worker node takes its local partitions of the large table and performs a hash join against a full, 
in-memory copy of the small broadcasted table that has been sent to that node.
- Parallel execution: Because the large table is untouched and stays localized, the join executes much faster by avoiding expensive shuffle I/O operations.

Since AQE is disabled it will create 200 partitions when we join the Fact with the Dim table or perform any wide transformations. 
In each of the 200 partitions it will put the Dimension key from the Fact and the Dim tables so that they can be joined together.
So these 200 partitions will be shuffled and will executed on the 4 executors. 

We can avoid these shufflings or avoid creating 200 partitions.Condition is one table should be very large in size and one very small.So small that it can be broadcasted to the Driver node and stored in 
Executor memory.

The Driver node will load the 1 MB Dim partition into its JVM memory and broadcast it to all the 4 executors.
All the executors now have the data to perform joins so there is no need for shuffling.

D.CACHING & PERSISTENCE -- Create another notebook 'CACHING & PERSISTENCE'
---------------------------------------------------------------------------
Spark Pool Memory --> Divided into 2 parts |Storage memory|  AND |Execution memory|
Execution memory is short-  lived memory. It will simply evict a existing dataframe if it wants to accomodate a new dataframe.

So suppose we create multiple dataframes .
df1 = .csv (read)
df2 = (transformation 1)
df3 = (read from df1 and do transformation2)
df4 = (read from df1 and do transformation3)

When we are creating df2 after df1,it will evict the dataframe (df1) from Execution memory.
So if we want to refer to df1 again it will recalculate it using DAG.
Again for df3 & df4 if it is referring to df1 it will recalculate df1 using DAG because df1 is evicted and not stored anywhere in memory.

Long term memory is the Storage memory which is used for caching. So if we are using a dataframe multiple times and if the dataframe is not big in size,
it is better if we do caching and store it in the Storage memory. So instead of recalculating from DAG it will use the dataframe from storage cache and processing 
will be much faster.

So for df2 , df3 and df4 , instead of recalculating df1, it will be much faster if the dataframe df1 is read from cache.

df.persist(storageLevel.DISK_AND_MEMORY)  = df.cache()

Two other options -
- DISK_ONLY
- MEMORY_ONLY 

a) storageLevel.DISK_AND_MEMORY -> If the caching dataframe is very big and cannot be accomodated inside storage memory. So Spark will try to fit as much partitions as possible
into the memory and the rest into the disk. 

b) DISK_ONLY --> Cache the data onto disk. Not recommended.
c) MEMORY_ONLY --> So if our dataframes are very small and can be accomodated inside the storage memory without any issue we can use this option.
c) MEMORY_AND_DISK_2 --> ) Replicates every cached partition across two separate worker nodes, providing fault tolerance if a machine fails.
d)MEMORY_ONLY_SER / MEMORY_AND_DISK_SER--> : Serializes the DataFrame into a space-efficient byte stream before caching. 
This significantly reduces the memory footprint but introduces CPU overhead for serialization and deserialization
e) To unpersist --> df.uncache()

E. Dynamic Resource Allocation
---------------------------------------------------------------------------------------------------------
Suppose there are 100 cores , 1 driver and 20 Executors . So if a developer is submitting his or her Spark application 'spark-submit' . 
All those resources will be locked and cannot be used by others until the Spark application gets submitted.
This is static resource allocation.

spark-submit\
--conf spark.dynamicAllocation.enabled = true \
--conf spark.shuffle.service.enabled = true   \
--conf spark.dynamicAllocation.minExecutors=2\
--conf spark.dynamicAllocation.initialExecutors=4\
--conf spark.dynamicAllocation.maxExecutors=10\
my_spark_job.py

The solution is 'Dynamic Resource Allocation' .
I will put a demand to the cluster manager that I need 10 executors but I don't want to lock my resources, I want to make them dynamic. 
So if after a idle time of say 60sec. if my executors are in a idle state and not processing anything they will be released.
So out of 20 executors 19 are released .

So what if I need 2 more to process my data ? (conf spark.dynamicAllocation.minExecutors=2)
A) So I will say that I need at least two executors so even after the time window of 60 sec. those two executors will not be released.

B) So if we need more executors we can get but not more than 10.(conf spark.dynamicAllocation.maxExecutors=10)

c) So what if we typically need more executors while starting the Spark application or while reading some data , transformations , pruning and all that 
we will use the parameter 'conf spark.dynamicAllocation.initialExecutors=4' to start with initially out of which only 2 will remain even after idle time.

G.Dynamic Partition Pruning
------------------------------------------------------------------------------------
So we have a partitioned dataframe . Each partition folder contains partition files. Eg: partitionBy("Date") will have folders like '2022' ,
'2023','2024','2025', '2026' . So partition pruning is basically filtering out the data that is not required based on partition value like date so that all the folders do 
not get scanned.

We have another dataframe which is not partitioned.We just have only 1 file.

df1.filter("")\
   .join("")
   
We are applying a filter condition on df1 so instead of scanning all the files it will only join those files which actually meet the join criteria.

But if we want to apply filter on df2 and then join to df1.There will be no partition pruning since filter is not applied on df1 and df2 will join df1,on all the available files 
whether it meets the join criteria or otherwise.

df2.filter("")\
     .join("")
     
This is where Dynamic Partition Pruning comes into the picture.
It will pass or broadcast the df2 filter to df1 during runtime.It will create a select query on top of the df2 keys and will pass that query as a filter to df1.
So it doesn't need to read all the partitions. But only those that satisfy the filter conditions.

We can prune partitions even if we do not have filter on one of the dataframes or tables because we can use filter of the other table.

 H.Broadcast Variable
 ---------------------------------------------------------------------------------------------------------------------------
Broadcast variables allow the programmer to keep a read-only variable cached on each machine rather than shipping a copy of it with tasks. They can be used, for example, 
to give every node a copy of a large input dataset in an efficient manner. Spark also attempts to distribute broadcast variables using efficient broadcast algorithms to 
reduce communication cost.

Broadcast variables are created from a variable v by calling SparkContext.broadcast(T, scala.reflect.ClassTag<T>). The broadcast variable is a wrapper around v, 
and its value can be accessed by calling the value method. 

After the broadcast variable is created, it should be used instead of the value v in any functions run on the cluster so that v is not shipped to the nodes more than once.
 In addition, the object v should not be modified after it is broadcast in order to ensure that all nodes get the same value of the broadcast variable 
 (e.g. if the variable is shipped to a new node later).
 
 
 Suppose there is a UDF and we are using a dictionary variable inside it.

     }
 So instead of sending this variable to the executors one at a time , again and again we broadcast it to all the executors in all the jobs so that it resides in their memory.

-----------------------------------------------------------------------------------------------------------------------------------------

user_id | purchase

So if we apply a groupBy(or any wide transformations) , it will create one partition for every user_id . For B and C Ids it will be normal sized partitions but for 
user id A the partition size will be huge.

So while the partition size of user Id A is  1.5GB the executor which will process this partition only has 1GB memory.
This will lead to driver OOM (Out-of-Memory) error because we do not have enough memory to process this partition.

Salting           --> We will try to add some numbers or other values to break this large-sized partition into smaller chunks.The numbering will be random but I can select the 
range, eg: 0-1, 0-2, etc. 


user_id | purchase  | salt
-------------------------------
A       | 100       | 0
A       | 200       | 1 
A       | 300       | 0 
B       | 400       | 0
C       | 500       | 1

We will add a new column to the above dataframe / table that will be a concat of the 'user_id' and the 'salt' column.

user_id | purchase  | salt  |  NewCol
--------------------------------------
A       | 100       | 0     |  A0
A       | 200       | 1     |  A1
A       | 300       | 0     |  A0
B       | 400       | 0     |  B0
C       | 500       | 1     |  C1

Now instead of the big sized partition of only user_id 'A' we will create partitions based on the NewCol. So we will have partition for 'A0' , one for 'A1' , one for 
'B0' , etc. So we have now broken down the big partition into smaller chunks.
