Q3. What are the key differences between Spark and Hadoop MapReduce in terms of performance and scalability?
A. Spark vs. Hadoop MapReduce: performance and scalability
Performance

In-memory vs. disk-based execution:
MapReduce writes intermediate results to disk (HDFS) after every map and reduce stage. 
Spark keeps intermediate data in memory where possible and spills to disk only when needed. 
For iterative workloads (ML, graph algorithms) and multi-stage pipelines, Spark is often 10-100x faster in memory and still meaningfully faster on disk, 
thanks to fewer materialization points.

DAG execution vs. rigid two-stage model
MapReduce forces every job into map → shuffle → reduce, and complex logic means chaining multiple jobs, each with its own read/write cycle. 
Spark builds a DAG of the whole computation, pipelines narrow transformations within a stage, and optimizes across the entire plan. 
With Spark SQL and DataFrames, the Catalyst optimizer (predicate pushdown, column pruning, join reordering) and Tungsten (off-heap memory, whole-stage code generation) 
add further gains. Adaptive Query Execution can then tune shuffle partitions, join strategies, and skew at runtime.

Task and startup overhead
MapReduce launches a new JVM per task, which adds latency. Spark reuses long-lived executors, so tasks start in milliseconds, 
which matters for interactive and short-running queries.

Latency and workload types
MapReduce is batch-only. Spark covers batch, interactive SQL, streaming (Structured Streaming), ML (MLlib), and graph processing in one engine, 
avoiding data movement between separate systems.

Scalability
Aspect	                                                   MapReduce	                                                         Spark
Horizontal scaling	                            Proven to thousands of nodes.	                                        Also scales to thousands of nodes.
Fault tolerance	                        Re-run failed tasks; intermediate data is on disk	                     Recompute lost partitions via RDD lineage;
                                                                                                                     checkpointing for long lineages
Data larger than memory	                    Naturally handled (disk-based)	                               Handled via spill to disk, but needs tuning to avoid OOM and GC pressure
Resource management	                                      YARN	                                                     YARN, Kubernetes, Mesos, standalone
Storage coupling	                                Tightly tied to HDFS	                               Storage-agnostic (HDFS, S3, ADLS, GCS, Delta/Iceberg tables)

• .orderBy('wordcount', ascending=False): Sorts the final list so the most frequent words appear at the top.
• .display(): Renders the final DataFrame as a visual table (commonly used in Databricks).

Q16. What is the Query Optimization ?
A.
Query Optimization in Spark is the process by which Apache Spark transforms a user’s high-level code (written in SQL, Python, Scala, or R) into the most efficient, 
low-level physical execution plan.
Instead of executing your code exactly as written, Spark acts like a relational database compiler. It evaluates the structure of your data and your target transformations 
to eliminate redundant steps, minimize expensive data shuffling across the network, and maximize cluster performance.


The Architecture: How Spark Optimizes Queries

Spark performs this magic using an extensible framework called the Catalyst Optimizer, operating through a structured, multi-stage pipeline:
    
                                                     Logical plan             Physical plan
 [ Your Code ] ➔ 1. Parsing ➔ 2. Analysis ➔ 3. Logical Optimization ➔ 4. Physical Planning ➔ 5. Code Generation (Tungsten)
 
 1. Parsing: Spark passes your query through a parser to check basic syntax, turning it into an Unresolved Logical Plan (an Abstract Syntax Tree or AST). 
 At this stage, Spark knows what you want to do, but doesn't know if the tables or columns actually exist yet.
 
2. Analysis: Spark consults its internal dictionary (the Catalog) to validate the names of tables, dataframes, and columns, as well as data types.
Once everything is matched and validated, it becomes an Analyzed Logical Plan.

3. Logical Optimization: The Catalyst Optimizer applies a set of rule-based rewrites to streamline the operations.
It rearranges the query components to produce an Optimized Logical Plan.

4.Physical Planning: Spark converts the logical plan into one or more possible Physical Plans (which dictate the exact distributed cluster operations,
like choosing between a SortMergeJoin or a BroadcastHashJoin). It then uses a Cost-Based Optimizer (CBO) to calculate which plan consumes the least CPU, memory,
and network resources, selecting the absolute winner for execution.

5. Code Generation: Finally, the Tungsten Execution Engine compiles the chosen physical plan into highly optimized Java bytecode (Whole-Stage Code Generation) 
to run natively and swiftly on your cluster workers.


Core Optimization Techniques Applied by Catalyst

When modifying the logical plan, Spark automatically applies several classic relational data optimization rules:
   i) Predicate Pushdown (Filter Pushdown): Spark pushes your WHERE or filter() clauses down as close to the data source as possible.
    If you have a billion rows but only want data where country = 'US', Spark filters the rows during the initial read step rather 
    than pulling a billion records into memory first.
    
   ii) Projection Pruning (Column Pruning): Spark identifies which columns are actually used in your final output. 
   If your table has 100 columns but you only select 3, Spark ignores the other 97, sharply cutting down memory consumption 
   and network load (especially effective when reading columnar formats like Parquet) 
   
   iii) Constant Folding: Spark evaluates expressions containing constant values at compile time rather than computing them for every single row. 
   For instance, an expression like 1 + 2 is simplified immediately to 3.
   
   
Modern Runtime Enhancements

Static optimization cannot predict everything. Because data sizes change mid-job, modern versions of Spark incorporate two powerful dynamic layers:
    
      i) Adaptive Query Execution (AQE): Enabled by default, AQE looks at the actual metrics collected during query runtime and re-optimizes the physical plan on the fly.
       It automatically collapses small partitions to avoid overhead, automatically converts massive shuffle joins into rapid broadcast joins if the intermediate data 
       is small enough, and balances out skewed partitions.
       
      ii) Dynamic Partition Pruning (DPP): When you are joining a large fact table with a small dimension table, DPP allows Spark to bypass reading irrelevant 
      partitions from the large table by executing the dimension table's filters at runtime.

 Q19. What is the use of COALESCE() and REPARTITION() ?
 A. It's always better to read from a few optimized , bigger sized partitions than from multiple smaller sized partitions .
 COALESCE()is used to always reduce the number of partitions . It doesn't require shuffling.
 
 REPARTITION() can be used to increase or decrease the number of partitions.
 So if we have two very big partitions and we want to redistribute the data across multiple partitions and nodes we can use the REPARTITION.
 It requires shuffling.

data compaction) , plus 'ZORDER BY' will sort the data in either ascending or descending manner within these 2 partitions.

Spark will get the statistics from the transaction logs.(We get column statistics for the first 32 columns)

P1
|-------------      min & max value --> 1   &    5
| 1,2,3,4,5  |
|------------|

P2
|-----------|
|6,7,8,9,10 |       min & max value ----> 6 & 10
|-----------|

So if we are using a query 'select * from tabledelta where ID <= 5;' 

If we had not used the 'ZORDER BY' command, data read would have been from both the partitions. But since Spark has the statistics for the minimum and maximum value it will 
read the data from partition 1 and skip partition 2(data skipping).
