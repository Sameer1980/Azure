Q1) You have a Spark job that needs to process 10GB of data. How would you decide the number of cores and memory per executor for this job?
Explain your reasoning.

A)EXECUTOR - say 10 GB
Inside a Executor / Spark Pool:
 Spark Executor Memory or JVM Heap Memory(spark.executor.memory):
This is primary block managed by the JVM where your actual Spark code executes.
It is strictly subdivided into four distinct spaces:
A) Unified Memory Pool(Default 60% or 6GB-300MB of remaining heap):The core space where Spark handles data processing. This pool dynamically shares memory between two segments based on workload demands. Divided into two parts- 
                                         i)Storage Memory(caching) 50%- Used for caching data frames, storing RDD persistence states, and handling broadcast variables.
                                          ii) & Execution Memory 50%- Used for intensive computational operations like shuffles, joins, sorts, and aggregations.
B)User memory = 40% (4GB - 300MB)- Used for non-Spark operations, such as user-defined data structures, custom RDD transformations, internal metadata, and User-Defined Functions (UDFs).It is controlled by 1 - spark.memory.fraction.
C)Reserved memory:(Fixed 300MB)-  Hardcoded safety buffer reserved entirely for Spark’s internal framework processes. It cannot be adjusted or used for your tasks. If your overall heap size is too small (less than 450 MB), Spark will throw a "please use large heap size" error.

128MB = 1 partition
10 GB data = 80 partitions

[Calculation: 10GB * 1024MB = 10240MB 
10240MB / 128MB/partition = 80 partitions]

80 partitions -> 80 cores -> 10 executors (8 cores per executor)

1 partition -> 1 task -> 1 core 

8 cores = 8 partitions(128 MB each) = 1GB

as 'SchemaLocation' folder.

Autoloader schema evolution. - Modes -> a) addNewColumns - Stream fails and new columns are added to the schema, b) rescue- Schema is never evolved and stream does not fail due to schema changes.All new columns are 
recorded in the '_rescued_data' column ,c) failOnNewColumns - It will simply fail the stream, d) none- Does not evolve the schema , new columns are ignored and data is not rescued.
Stream does not fail due to schema changes.

 Classic - Supports Photon Engine.
Pro - Supports Photon Engine and Predictive IO.
Serverless - Supports Photon Engine, Predictive IO and Intelligent Workload Management(IWM).
  
Whenever we pick the Classic and Pro SQL Warehouses we pick the cluster size. Eg: 2X-small , X-small, Small, Medium, Large, X-large ,etc.
For Classic and Pro SQL Warehouses, autoscaling adds clusters based on the estimated time to process all running and queued queries. 
So if we have added a medium size clusters of 8 workers it will add another cluster of the same size and number of workers.	

- 2-6 min. of query load: Add 1 cluster
- 6-12min.: Add 2 clusters
- 12-22 min: Add 3 clusters
- Over 22 min. : Add 3 clusters plus 1 more for every additional 15 min. of load. 

Sizing and cluster provisioning:
When creating a classic and pro warehouse , choose a cluster size and set the minimum and maximum number of clusters. These SKUs have a fixed limit of one cluster per 10 
concurrent queries.

For a serverless SQL Warehouse - Cluster size (eg: X-small, Medium, Large) determines the compute resources available for a single cluster. The AutoScaler adds or removes clusters 
of that size as needed. Since it uses IWM(Intelligent Workload Management) it can predict better.

  scale up.
- If queries are spilling to disk, increase the cluster size. Check for spills in the query profile.
- For workloads with many concurrent queries, configure a sufficient maximum number of clusters to handle peak loads.

Q16) You have a large Delta table in Databricks(billions of rows) used for analytics. Due to data privacy rules, you need to delete a small subset of records frequently(for example
     user-requested deletes). Rewriting the entire data files every time is slow and expensive.

How do deletion vectors in Databricks help in this scenario? 
What do they do under the hood, and how do they improve performance compared to traditional deletes?

A) 1)Deletion vectors in Databricks implement a merge-on-read (soft delete) approach for Delta Lake and Apache Iceberg tables to accelerate DELETE, UPDATE, and MERGE operations.
2) Deletion vectors avoid full rewrites.Without deletion vectors, modifying or deleting even a single row requires rewriting the entire Parquet file that contains that record,
causing heavy write amplification.
3) With deletion vectors enabled, Databricks does not rewrite the Parquet file immediately.Instead, it marks the deleted or updated rows using a compact bitmap format
(like a RoaringBitmap) stored in metadata (either in the Delta transaction log or as separate sidecar files).

4)Read-Time Resolution:When you query the table, the query engine reads the active Parquet data files and dynamically applies the deletion vector metadata 
at query time to filter out the logically deleted rows.

5)When we have a Delta table and we do a delete it adds one new parquet file . So if we have 3 files and we are deleting from file1 , file4 will be added and all records(billion rows)
from file1 minus the deleted records will be loaded into this file. 

So if we have a Deletion Vector enabled it will not rewrite the whole file but it will create a file named as 'Deletion Vector' .It will store what records to delete?
It can be metadata, IDs, other data, anything.

So when we are trying to read the data we are using the same files but we have something called as Deletion Vector. So we will not read those records that are deleted.
In the parquet file1 records will be marked as deleted using the Deletion Vector. So when we are reading the file or the data we will not display those records.
This way we do not need to rewrite the billions of records again and again.

Q18) You have a Delta table with 2-3 TB data where new records are continuously appended.
     Earlier it was partitioned by date, but now queries filter on customer_id and region, and partitions are causing too many small files.

    How would liquid clustering help here, and why it is better than traditional partitioning? 

A) Earlier partitioned data(parquet files) used to be stored on different folders. So if partitioned by date, one folder would be '2023', another folder '2024', '2025',....etc.
   So millions of small files would be created and it would lead to small files problems and lot of overheads would be created to manage those partitions.
   With Liquid Clustering we do not need to do any sort of partitioning. It will create a kind of Logical Clusters/Partitions. Not physical but logical partitions.
   As new data gets appended, Databricks will automatically cluster the files based on certain columns. Those columns that we will pick for Liquid Clustering.
  Similar values will be clubbed together and this will help to fetch the data faster. So less data will be scanned and it will run faster. 
   Liquid Clusters are ever evolving. They will evolve with the query patterns as well.

When to use Liquid Clustering?
Databricks recommends liquid clustering for all new tables, including streaming tables and materialized views. 
- Tables that are often filtered by high cardinality columns.
- Tables that have skew in data distribution.
- Tables that grow quickly and require maintenance and tuning effort.
- Tables that have concurrent write requirements.
- Tables that have access patterns that change over time.
- Tables where a typical partition key could leave the table with too many or too few partitions.

SQL-
-- Create an empty Delta table with clustering on col0
CREATE TABLE table1(col0 INT, col1 STRING) CLUSTER BY (col0);

-- Create table from existing data with clustering
CREATE TABLE table2 CLUSTER BY (col0)
AS SELECT * FROM table1;

-- Copy table structure including clustering configuration
CREATE TABLE table3 LIKE table1;

-- Cluster by Auto. It will pickup the most suitable columns for Liquid Clustering.
CREATE OR REPLACE TABLE table1(column01 int, column02 string) CLUSTER BY AUTO;

-- Enable automatic Liquid Clustering on an existing table.
   ALTER TABLE table1 CLUSTER BY AUTO;

-- Disable automatic Liquid Clustering on an existing table.
 ALTER TABLE table1 CLUSTER BY NONE;

After enabling liquid clustering, Run OPTIMIZE jobs to incrementally cluster data.


1. Liquid Clustering (clusterBy)

When you use clusterBy("col0"), Spark applies modern layout techniques (like Delta Lake's Liquid Clustering).
• How it works: Instead of forcing data into rigid folders, Spark clusters the rows with similar col0 values together within the data files. It uses Z-order-like curves dynamically.
• Why use it: If col0 is something like customer_id or transaction_date with millions of unique values, clusterBy ensures your queries remain lightning-fast when filtering on col0 without creating a storage nightmare.
-No Folder Partitioning: Unlike traditional partition columns, liquid clustering does not create separate physical folder paths (such as year=2026/month=11/) on cloud storage.
Instead, it maintains a flat directory structure where similar values for your clustering keys are grouped together inside the data files.
- 


2. Partitioning (partitionBy)

When you use partitionBy("col0"), Spark uses traditional Hive-style partitioning.
• How it works: Spark creates a literal folder on your cloud storage/file system for every single unique value in col0.
• Why use it: This is highly effective for file pruning only if the number of unique values is small (typically under a few hundred). If col0 has thousands or millions of unique values,
Spark will create millions of directories and tiny files.This creates massive metadata overhead,slowing down your storage account and Spark itself.


Summary Recommendation

• Use partitionBy only if col0 has a very low number of distinct values (like region or year).
• Use clusterBy if you are using modern formats (like Delta Lake in Databricks/Spark 3.5+) and col0 has a high number of distinct values,
or if your data access patterns change over time.
