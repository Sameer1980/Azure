SPARK DECLARATIVE PIPELINES
---------------------------------------
When working with data in Spark , we often want to focus on WHAT we want to do with the data , rather than HOW Spark executes it under the hood. 
This is where declarative pipelines come in.
Unlike traditional imperative programming , where you give step-by-step instructions , declarative pipelines let you define a series of transformations
and actions on your data in a clean , readable way. Spark then figures out the most efficient execution plan.

They remove a lot of overheads like creating partitions, coalescing data , caching tables, and tuning performance.
Declarative pipelines handle these optimizations automatically.You don't need to worry about the low level mechanics .
Spark figures out the most efficient way to process your data .

You don't have to worry about execution details like task scheduling or memory optimization . Instead you describe a flow of operations like filtering, joining or 
aggregating and Spark handles the rest. This approach reduces bugs , improves performance and makes your data pipeline more robust.

Imagine you want to process a sales dataset to find the top products by revenue. In a declarative pipeline you'd describe your operations like -
read the dataset -> filter for completed orders -> calculate revenue -> group by product -> sort -> write results.
You don't tell Spark how to shuffle or partition the data . It decides the best way to execute your plan efficiently.

It also reduces code - Declarative pipelines also reduce the long, repetitive code that often comes with data engineering tasks . 
For example implementing SCD Type 2 manually involves writing a lot of steps for detecting changes , updating records and maintaining history.
With DP we can leverage tools like 'AutoCDC' which handles these operations automatically.

Key components : 
----------------

ref: https://learn.microsoft.com/en-us/azure/databricks/ldp/concepts 

A. Flows - A flow is the foundational data processing concept in SDP which supports both streaming and batch semantics. A flow reads data from a source , applies user-defined 
processing logic and writes the data into a target dataset. It's an end-to-end logic.

B. Datasets - A dataset is a queryable object that's the output of the flows within a pipeline.So when we write something to the destination it creates something .. it can 
be a table , view , etc. That object is called dataset . Three datasets are available within DP - Streaming Table , Materialized View , Temporary View .
There is one more dataset that's newly added that is called as Sink.So if we do not want to create dataset in Table format but just dump our data in the cloud storage.Eg:
a Azure datalake.
i) Streaming Table - It is a form of Unity Catalog managed table that is also a streaming target for Lakeflow SDP.
ii) Mat View - A Materialized View is also a form of UC managed table and is a batch target. 
iii) Temp View - A Temporary View is a view that holds the query and recomputes it.

C. Pipelines - A pipeline can contain one or more flows , streaming tables , and materialized views.It is basically the DAG of all the components .
All our objects will be converted into DAG.

We will a flow that contains a Materialized View .

A materialized view is a declarative pipeline object . It includes a query that defines it , a flow to update it , and the cached results for fast access.
A Materialized view :
A. Tracks changes in upstream data.
B. On trigger incrementally processes the changed data and applies the necessary transformations.
C. Maintains the output table , in sync with the source data , based on a special refresh interval .
In other words these are out incremental batch processing objects .

from pyspark import pipelines as dp
from pyspark.sql.functions import *

# Materialized View
@dp.materialized_view
def src_sales(name = "src_sales"):
    df = spark.read.table("sdp_catalog.source.sales")
    df = df.withColumn("date", to_date(col("date"),"MM-dd-yyyy"))
    return df

#Materialized View (referring to another materialized view)
# Silver layer
@dp.materialized_view(name = "enr_sales")
def enr_sales():
    df = spark.read.table("src_sales")
    df = df.withColumn("revenue",col("revenue") * 1.05)
    return df

#Materialized View (referring to another materialized view)
# Gold layer 
@dp.materialized_view(name = "cur_sales")
def cur_sales():
    df = spark.read.table("enr_sales")
    df = df.groupBy("date").agg(sum("revenue").alias("total_revenue"))
    return df

from pyspark import pipelines as dp
from pyspark.sql.functions import * 

# Creating empty streaming table
dp.create_streaming_table("total_sales")


# Appending North Sales to the 'total_sales'
@dp.append_flow(target = "total_sales")
def north_sales():
    df = spark.readStream.table("sdp_catalog.source.sales_north")
    return df

# Appending South Sales to the 'total_sales'
@dp.append_flow(target = "total_sales")
def south_sales():
    df = spark.readStream.table("sdp_catalog.source.sales_south")
    return df
