Optimizing with Delta Engine in Databricks.
----------------------------------------------
Delta engine is only available in Databricks. It is a high performing query engine built into Databricks Runtime helping to process and query data 
faster than the Spark engine . 

Can work with any data format including Delta .

There are three components of Delta engine - 
       - Query Optimizer
	   - Photon Execution Engine.
	   - Delta Cache .
	   
Delta engine Query Optimizer features :
      -  Data Skipping
	  - Bin-packing & Z-Order optimizations.
	  - Vacuum
	  - Auto-optimization
	  - Data transformation optimizations
	  - Join & Low shuffle merge optimizations
	  
Some of Delta engine optimizations are making their way to open-source Delta Lake .

Improving Performance with Statistics and Data Skipping.
-------------------------------------------------------------
With each transaction log entry , statistics are computed and stored . 

Sample transaction log entry .

{"commitInfo": {"timestamp": 1640067393982, "userId": "1472626815582251",
  "operation": "WRITE" , "operationParameters":{"mode":"Append"},
  "operationMetrics":{"numFiles":"2", "numOutputBytes": "7284" , "numOutputRows": "200"}}}
  
  How Data Skipping works ?
  
  Suppose there are three part files.

    File1:                       -------->                Stats computed 
 EmpId  |  Salary                                       Column  | Minimum  | Maximum
 1      |  10,000                                        EmpId  |     1    |    3
 2      |  13,500                                        Salary |  10,000  |  15,000
 3      |  15,000
	  
 
 File2:                         --------->               Stats Computed 
 EmpId  | Salary                                        Column |  Minimum   | Maximum
 4      | 18,000                                        EmpId  |  4         |    5
 5      | 21,000                                        Salary |  18,000    |  21,000


File3:                         ---------->              Stats Computed 
EmpId  | Salary                                       Column | Minimum | Maximum
6      | 14,000                                       EmpId  |  6      |   8
7      | 16,500                                       salary |  14,000 | 19,000
8      | 19,000 
  
  
All these stats are stored in the Transaction log.

SELECT * 

FROM Employees

WHERE Salary BETWEEN 16000 AND 17000 

Files 1 & 2 will be rejected based on computed stats.
File 3 will be selected .

There is only record with salary 16500 and that will be selected .

Data skipping :
     -   First checks the statistics in the log.
	 -   Reads only files which fall within range of filter conditions.
	 -  Rest of the files are skipped.
	 
This can significantly improve query perfomance .

Optimizing & Z-Ordering Delta Table.
----------------------------------------

Optimize Options

  -  Bin-Packing / File Compaction
  -  Z-Ordering

Suppose there is a 'Customer' folder in the data lake containing over 200 files .
Continuosly writing data to a table adds multiple small files over a period of time.
Reading too many small files involves lot of overhead .(small files problem)

In Delta Lake this can be solved by using Bin-Packing or File Compaction feature.
To use it we can use the Optimize command on Delta tables. This will take data from small size files and pack it into bigger size files.
Data is compressed and stored in new evenly-balanced , larger files of optimal size.

- Default max size is 1GB which can be changed.
- Previous files are still there to support time travel.

Run Optimize periodically depending on number of operations on your table !
Scenario 2:
Suppose there are three files -
File1:

Id | City
1  | Seattle
2  | Paris
3  | Delhi

File2:

Id | City
4  | Delhi
5  | London


File3:

Id | City
6  | Zurich
7  | Seattle
8  | Delhi

The record for Delhi is present in all three files.This means all three files should be opened to get the data .

SELECT *
FROM Customer
WHERE City = 'Delhi';

These scenarios can be optimized by using Z-Order Optimization.
Use OPTIMIZE ZORDER BY (City). It will create new files but data will be sorted by City column and then stored in the files.
File 4:
Id | City
3  | Delhi
8  | Delhi
4  | Delhi
5  | London 

File5:
Id | City
2  | Paris
7  | Seattle
1  | Seattle
6  | Zurich

SELECT *

FROM Customer

WHERE City = 'Delhi';


Data will be picked up from one file only (File4) while the other file(File5) will be ignored bacause of Data Skipping.

When we run OPTIMIZE ZORDER BY (City) command it performs Bin-packing but along with that data is sorted and co-located in files based 
on Z-Order columns .

Very similar to cluster-indexing a database.

Improves perfomance by data skipping.

** Note: Use columns which are frequently used in filters , joins and grouping queries .
** Note : Bin-packing and Z-Ordering are CPU intensive, costly operations because of physical reorganization of data .

---------------------------
Insert (add 4 records)

Part1 File:

                                                                 000.json

3  |  C                                                          Add        |   Part1
4  |  D                                                          Add        |   Part2

                                                                 001.json
Part3 File:                                                       Operation   |   File Name      
Id |  Name                                                        Remove      |   Part1
2  |   B                                                           Add        |   Part2


Part 1 File can be used for time travel .
But suppose we don't want to use this file and want to clean up. 
This is where Vacuum command is used.
VACUUM permanently deletes unreferenced Parquet files that are older than your retention threshold. The transaction log might still know about those versions, but the data they depend on is gone.
Vacuum command physically removes data files.
           -  Files that are no longer referenced in the latest transaction log state .
           -   And files that are older than a retention threshold.(default is 7 days)
		   
	Affects time travel.
	Tip: Set the retention period for time travel and run Vacuum periodically !! 

ALTER TABLE  my_catalog.new_schema.vehicles SET TBLPROPERTIES (
  'delta.logRetentionDuration' = '30 days',
  'delta.deletedFileRetentionDuration' = '7 days'
);
	
Cleaning Files with Vacuum:
DESCRIBE HISTORY TaxisDB.YellowTaxis;
Switch over to Azure Data lake folder to check the files in data lake.

VACUUM TaxisDB.YellowTaxis
RETAIN 0 HOURS DRY RUN;

Delta Lake maintains two separate retention settings, and mixing them up is one of the most common reasons time travel fails unexpectedly.
Transaction Log Retention (logRetentionDuration)
Default: 30 days
Keeps the metadata that describes each table version
Enables commands like DESCRIBE HISTORY to show past versions

Data File Retention (deletedFileRetentionDuration)
Default: 7 days (168 hours)
Keeps the actual Parquet files that older versions depend on
Files are permanently removed by the VACUUM command.

Specifiying 0 hrs. will delete all previous versions. Use DRY RUN clause .
It will not actually delete the files but return a list of files to be deleted.

If we don't retention hrs. by default it is 7 hrs.
Databricks will give us a warning about deleting files with such a low retention period.So it is important to set the right retention period.
But if we still want to delete all previous versions.
SET spark.databricks.delta.retentionDurationCheck.enabled = false

Again run. 

VACUUM TaxisDB.YellowTaxis
RETAIN 0 HOURS DRY RUN;

It will return a list of files to be deleted by Vacuum as they are not referenced by the latest version of the table.
Run Vacuum again to physically delete the files.

VACUUM TaxisDB.YellowTaxis
RETAIN 0 HOURS ;

Verify from the Azure portal to check whether files have been physically deleted or not.
Again check Transaction Log.
DESCRIBE HISTORY TaxisDB.YellowTaxis;

Enabling Auto Optimization on Delta tables.
------------------------------------------------
Auto Optimize features:- 
Optimized Writes                                        Auto Compaction                                       
(Auto bin-packing while writing)                     (Auto bin-packing after writing)

Suppose we have a Job(process sales data) . Spark will create optimal tasks that will write optimal size part files to the data lake.

Optimized Writes -
  - While writing data , Databricks dynamically tries to create - 128 MB Partition Files.
  - Prevents creation of small files without sacrificing parallelism , but with slight overhead.
  - No need to run Optimize command later.
  
  Use cases -
      -  Helpful when loading streaming data.
	  -  When performing DML operations on table.
	  
Auto Compaction -
    -  Immediately after writing , Databricks further checks partition files in Delta folder.
	- Any non-compacted files are compacted to - 128 MB.
	- Only runs when there are more than 50 small files.
	- No need to run Optimize command later.
	
Use cases -
      -  Helpful when loading streaming data.
	  - Where Optimize command is called after each write.

Using Delta Cache 
-----------------------

Two types of caching available in Databricks .

1. Apache Spark Cache (Part of Spark)

2. Delta Cache (Part of Delta Engine) 

How Delta Cache works?
    - Works for Parquet and Delta formats .
	- Files are read from the external storage for the first time.
	- Stored on local disks of cluster machines .
	- Successive reads of same data are served using local files , improving query performance.
	
Cache is automatically invalidated / evicted if :
       - Underlying files are modified.
	   - If Cluster is restarted all cache files are removed.
	   
How to use Delta Cache ?

   - Use Delta Cache Accelerated VMs as worker machines - caching enabled by default.
   - Explicitly enable cache on other VM types.

To use Delta Cache we can use Cluster with Delta Cache Accelerated VMs.   

Click on 'Create Cluster' --> from 'Worker Type' select 'Delta Cache Accelerated VMs'.

Use a cluster with non-delta cache enabled VM.
